## 1. RBI Data Localization (UPI Transaction Data)

### The rule

The Reserve Bank of India's circular on *Storage of Payment System Data*
(6 April 2018) requires that all data generated by payment systems
authorized by RBI — including UPI transactions — be stored **only** in
India. This covers:

- End-to-end transaction details (payer, payee, amount, timestamp, outcome)
- Customer-facing data (UPI ID, VPA, mobile number, KYC)
- Any data used to deliver the payment instruction or settlement

### Current TrustRail posture

❌ **Not compliant.** The current demo runs in a single sandbox VM whose
physical location is not guaranteed to be in India. SQLite database at
`db/custom.db` and the JSONL logs at `trustrail-ml/data/*.jsonl` contain
payer IDs, payee IDs, amounts, and timing data — all of which constitute
"payment system data" under the RBI circular.

### Required changes before production

1. **Pin the deployment to an Indian region.** AWS `ap-south-1` (Mumbai),
   Azure `Central India`, GCP `asia-south1`, or an Indian datacenter
   provider (CtrlS, ESDS, Nxtra).
2. **Replication boundary.** No cross-border replication for backups or
   read replicas. Backups must also stay in India.
3. **Vendor due diligence.** Confirm that any SaaS dependency (e.g.
   observability tools like Datadog) either has an India region or is
   configured to drop payload data before it leaves the country.
4. **Data Processing Agreement (DPA).** Required with every vendor that
   touches the data, even transiently.

### Estimated cost / effort

- AWS Mumbai region pricing is roughly 1.1× us-east-1 — manageable.
- The bigger lift is the DPA review with each vendor — budget 4–6 weeks.

## 2. NPCI Certification (UPI)

### The rule

The National Payments Corporation of India (NPCI) operates UPI. Any entity
that processes UPI transactions on behalf of others must either:

- Be a **Payment Aggregator – Cross Border (PA-CB)** or **Payment
  Aggregator (PA)** authorized by RBI, OR
- Operate **under the PA license of a partner** bank or PSP (the
  "sponsor-bank model")

TrustRail's value proposition — routing decisions across gateways — would
fall under the sponsor-bank model unless TrustRail itself becomes a PA.

### Current TrustRail posture

❌ **Not addressed.** No NPCI certification, no sponsor-bank agreement.
The current demo only processes synthetic transactions, so no real UPI
data flows through the system.

### Required steps before production

1. **Sign a sponsor-bank agreement** with an Indian bank that holds a PA
   license. Likely candidates: Razorpay's banking partners (RBL, ICICI),
   Cashfree's, or directly with a smaller bank (Equitas, Federal, Yes).
2. **NPCI UPI certification** — the sponsor bank sponsors you through
   NPCI's onboarding. Expect 3–6 months.
3. **Compliance with NPCI's UPI Procedural Guidelines** — covers data
   formats, security standards, dispute resolution.
4. **Implement the NPCI-mandated audit log format** — every routing
   decision must be replayable for 7 years (already partially done via
   `decisions.jsonl`, needs tamper-evidence — see Section 5).

### Estimated cost / effort

- Sponsor-bank agreement negotiation: 3–6 months, ₹5–25L in setup fees.
- NPCI onboarding: 3–6 months, technical + legal review.
- This is the single longest pole in the tent — start early.

## 3. PCI-DSS Posture

### The rule

The Payment Card Industry Data Security Standard (PCI-DSS) applies to any
system that stores, processes, or transmits cardholder data. TrustRail
does NOT handle card data — it operates at the payment gateway routing
layer, where card data is already tokenized by the gateway.

### Current TrustRail posture

⚠️ **Not applicable yet.** The current demo does not process card data,
so PCI-DSS does not apply. However, any future integration with card
networks (Visa, Mastercard, RuPay) would require compliance.

### Anticipated scope when card data is involved

The lightest tier is **SAQ-A** (Self-Assessment Questionnaire A), which
applies when:
- Card data is fully outsourced to a PCI-compliant third party (e.g.,
  Stripe, Adyen, Razorpay's card tokenization)
- TrustRail's servers never see raw PAN, CVV, or expiry dates
- All cardholder-facing pages redirect to the third party's hosted page

### Roadmap

1. **Confirm SAQ-A scope with the card gateway partner.** Stripe and
   Adyen both support a SAQ-A posture via their hosted payment pages.
2. **Annual self-assessment** — SAQ-A is ~$1,000/year + 1–2 engineer weeks.
3. **Quarterly ASV scan** of external-facing IP addresses — ~$500/quarter.
4. **Upgrade path**: if TrustRail ever tokenizes cards itself, scope
   jumps to SAQ-A-EP or full PCI-DSS Level 1 — avoid this unless
   absolutely necessary.

### Estimated cost / effort

- SAQ-A: ~$2K/year + 1–2 engineer weeks for annual review
- Full PCI-DSS Level 1: $50K–$150K/year + dedicated security engineer —
  defer unless business case is overwhelming

## 4. PII Handling (Payer / Payee IDs)

### Current state

⚠️ **Plaintext in SQLite.** The `Transaction` table in `prisma/schema.prisma`
stores:

- `payerId` (e.g., `"payer_00001"`) — synthetic for the demo, but in
  production would be a real UPI VPA like `alice@okhdfcbank`
- `payeeId` (e.g., `"payee_00001"`) — same
- `amount`, `direction`, `hourOfDay`, `approvalLatencyMs` — behavioral
  metadata that, in aggregate, can identify individuals

Anyone with read access to `db/custom.db` (or the SQLite file on disk)
can read every payer/payee identifier in cleartext.

### Required changes before production

1. **Tokenization at ingest.** Replace `payerId`/`payeeId` with
   opaque tokens (`tok_payer_a1b2c3`) computed via a keyed HMAC. The
   mapping `real_id → token` lives in a separate, access-controlled
   vault (e.g., HashiCorp Vault, AWS KMS-backed envelope encryption).
2. **Encrypt the SQLite database file at rest.** Use SQLCipher
   (`PRAGMA key = '...'`) for transparent encryption, or move to
   PostgreSQL with `pgcrypto` for column-level encryption of PII fields.
3. **Field-level encryption for `finalActionReason` and `stage1Reasons`.**
   These contain human-readable context that may include PII ("first
   transaction from this payer to alice@okhdfcbank").
4. **Access logging.** Every read of the `Transaction` table must be
   logged with the operator's identity — supports post-incident audit.
5. **Retention policy.** Define how long transactions are kept.
   RBI requires 7 years for payment records; the DPDP Act may require
   deletion on user request — these are in tension and need a clear
   policy.

### Estimated cost / effort

- Tokenization: 2–3 engineer weeks for the API + vault integration.
- SQLCipher or PostgreSQL migration: 1–2 weeks.
- Field-level encryption: 1 week for schema changes + 1 week for key
  rotation tooling.

## 5. Audit Log Integrity

### Current state

⚠️ **Append-only JSONL, no tamper-evidence.** The `decisions.jsonl` and
`feedback.jsonl` files are append-only by convention but a malicious
actor with filesystem access could rewrite history.

### Required changes

1. **Chain-of-custody hashing.** Each log line includes a hash of the
   previous line — like a blockchain. Any tampering breaks the chain.
   ```python
   prev_hash = "0" * 64  # genesis
   for entry in entries:
       entry["_prev_hash"] = prev_hash
       entry["_hash"] = sha256(json.dumps(entry, sort_keys=True).encode()).hexdigest()
       prev_hash = entry["_hash"]
   ```
2. **WORM storage.** Write logs to S3 with Object Lock in Compliance
   mode, or to a dedicated audit log service (AWS CloudTrail Lake,
   GCP Cloud Audit Logs).
3. **7-year retention** as per RBI's payment system data storage rule.

## 6. DPDP Act 2023 (Digital Personal Data Protection)

### The rule

India's Digital Personal Data Protection Act, 2023 requires:
- Explicit, informed consent for collecting personal data
- Right to access, correct, and delete personal data
- Data breach notification within 72 hours
- Data Fiduciary registration for high-volume processors

### Current TrustRail posture

❌ **Not implemented.** The demo does not have a consent flow, no
data-subject access API, no breach notification procedure.

### Required changes before production

1. **Consent flow.** At first transaction, present a clear consent
   screen explaining what data is collected, why, and how long it's
   kept. Store consent timestamps per user.
2. **DSAR (Data Subject Access Request) endpoint.** `GET /user/me`
   returns all stored data for a given payer ID. `DELETE /user/me`
   deletes it (subject to RBI retention override).
3. **Breach notification runbook.** Document the 72-hour notification
   process to the Data Protection Board of India.
4. **Privacy policy.** Public-facing document at `/privacy`.

## 8. What this demo does NOT do

To set expectations clearly:

- **No real payment data** — only synthetic. None of the above compliance
  concerns apply to the demo build itself.
- **No multi-tenant isolation** — all transactions share one DB. Production
  requires per-tenant row-level security or separate databases per customer.
- **No authentication / authorization** — the login page is a UI demo; no
  real auth backend. Any credentials work.
- **No rate limiting** — the API is wide open. Production needs per-tenant
  rate limits + DDoS protection.
- **No key management** — no secrets in the codebase, but no real secrets
  exist either. Production needs a secrets manager (Vault, AWS Secrets
  Manager, Doppler).

Engage a payments lawyer + a SOC 2 consultant before any of this touches
real money.
